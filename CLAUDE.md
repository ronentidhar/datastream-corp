# CLAUDE.md

Working notes for this repo. See `README.md` for how to run the Phase 1 agents.

## Two environments

This repo lives twice:

| | Path | Role |
|---|---|---|
| Local | `~/development/ai/datastream-corp` | Editing, review, testing the deployed stack |
| Workshop box | `/workshop/datastream-corp` | Where AgentCore deploys actually run |

Changes reach the box by **push then `git pull`** — an edit made locally is not
live there until pulled.

`agentcore deploy` only works from the box. Its identity is an EC2 instance role
(`code-editor-CodeEditorInstanceBootstrapRole`); the credentials in
`aws-Strands/.env` are `WSParticipantRole`, which has no `s3:PutObject`, so the
deploy fails at the upload step locally. Both can read AgentCore, so status checks,
log queries, and invoking the deployed agent all work from either side.

The box is driven through a browser terminal that **mangles multi-line pastes** —
backslash continuations vanish, heredoc terminators get indented, long lines wrap
mid-string and break quoting. Hand over one genuinely short line, or put the logic
in a repo file and have it pulled. That is why `scripts/token.sh` exists.

## Layout

```
aws-Strands/        Phase 1 Strands agents (agent.py = orchestrator) + mcp_server.py
claude-sdk/         Claude Agent SDK ops monitor
lm-studio/          Local-model variant, no AWS
mcp-runtime/        Build dir for the MCP server deploy (generated)
agent-runtime/      Runtime agent deployed to AgentCore (agent.py is source, not generated)
scripts/token.sh    get_client_token / new_session_id / ask / ask_http
docs/               Framework comparisons
```

`runtime_deploy.sh` → `gateway_setup.sh` → `memory_setup.sh` → `deploy_agent.sh`,
in that order. Each is idempotent and records its outputs in `.env`.

**Build directories are uploaded wholesale**, so they must not contain `.env`.
`mcp-runtime/mcp_server.py` and both `requirements.txt` copies are generated by the
scripts — edit `aws-Strands/mcp_server.py` and the root `requirements.txt` instead.

## Environment files

- `.env` (root) — Cognito config plus every ARN/ID the scripts produce
- `aws-Strands/.env` — AWS credentials for Bedrock. **STS, so they expire**; an
  `ExpiredTokenException` means refresh these, nothing more.

Both are gitignored. Load with `set -a; source .env; set +a` — root `.env` mixes
bare `KEY=value` (written by the workshop) with `export KEY="value"` (written by the
scripts), and `set -a` exports both.

## Gotchas that cost real time

- **Session IDs pin to an agent version.** After a redeploy, reusing an old
  `--session-id` silently routes to the *previous* code — fixes appear to do
  nothing. Use `new_session_id` (min 33 chars). Reuse an ID only for a deliberate
  multi-turn conversation.
- **Forwarded headers keep their wire casing.** The runtime canonicalises only
  `Authorization`; HTTP/2 lowercases the rest, so look headers up
  case-insensitively. An exact-case `.get()` on the actor header silently collapses
  every caller to `default_user`.
- **A Gateway prefixes tool names** — `query_db` arrives as
  `datastream-mcp-target___query_db`. Match on the suffix, never equality.
- **`query_db`'s parameter is `query`**, not `sql`. The local-SQLite variants use
  `sql`; reading the wrong key yields `""`, which silently disables the write
  approval gate.
- **Memory retrieval is gated by `relevance_score`.** Short stored facts score
  ~0.35 against task-shaped prompts, so the sample's `0.7` discards everything.
  Tune via `MEMORY_RELEVANCE_SCORE`.
- **Semantic extraction is asynchronous** — allow ~60s before expecting a fact
  stated in one session to be retrievable in another.
- **`direct_code_deploy` needs `uv`** to cross-compile for Linux ARM64.
- **`get_client_token`** must resolve `.env` by absolute path; the workshop's
  original used a relative `source .env` and returned an empty token from any
  subdirectory, which the runtime rejects as an authorization-method mismatch.

## Verify, don't trust the task text

The workshop's instruction pages summarize rather than quote, and their sample code
has contained real bugs — a dead approval gate, a `DROP`-blind destructive check, a
credential provider name that does not exist in this account, a US-only weather API
for Israeli cities, and a relevance threshold that makes its own memory demo
unpassable. Check CLI flags with `agentcore <cmd> --help` and API shapes against
botocore's service model before writing code against them.

## The shared database

`mcp_server.py` proxies to a public endpoint shared with other participants and
accepts arbitrary SQL, including `DELETE` and `DROP`. Keep queries read-only unless
a write is the point of the task. Every row has `status = 'active'`, so filtering on
status changes nothing.
